# Para colar no SQL Editor do Clients_Base — 19/09/2026

Duas correções de higiene antes de fechar a entrega do CRM. Nenhuma muda
comportamento visível no painel; as duas evitam problema futuro.

Rode o bloco inteiro de uma vez. Ele está em transação: se algo falhar, nada é
aplicado.

## O que cada parte faz

**Parte 1 — trava otimista cega.** O parser promove Lead → Atendimento com um
UPDATE direto e nunca incrementou `stage_version`. Medido antes da correção:
**259 de 259** oportunidades em atendimento na versão 0. Resultado prático: a
tela carrega o card em Lead na versão 0, o parser move para Atendimento (ainda
versão 0), e a ação do usuário passa pela checagem de conflito como se nada
tivesse acontecido. A trava existe para esse caso exato e estava cega.

A correção fica no banco, não no parser — assim qualquer caminho que mude a
etapa incrementa a versão, inclusive código futuro. As RPCs já fazem o `+1`
explícito e continuam corretas: o trigger grava o mesmo valor.

**Parte 2 — ledger de migrations desalinhado.** Quatro migrations estão
registradas com o carimbo de quando foram aplicadas, não com o nome do arquivo
no repositório. Um `supabase db push` futuro tentaria rodar tudo de novo e
quebraria no `create function`. Além disso, `client_users_attendant_role` não
tinha arquivo nenhum no repo — foi escrito agora a partir do texto exato
guardado no próprio ledger.

## O bloco

```sql
begin;

set local lock_timeout = '5s';

-- ---------------------------------------------------------------------------
-- Parte 1: stage_version passa a ser incrementado em qualquer troca de etapa
-- ---------------------------------------------------------------------------

create function crm.bump_stage_version()
returns trigger
language plpgsql
security definer
set search_path = ''
as $fn$
begin
  if new.current_stage_id is distinct from old.current_stage_id then
    new.stage_version := old.stage_version + 1;
  end if;
  return new;
end;
$fn$;

revoke all on function crm.bump_stage_version() from public, anon, authenticated, service_role;

-- BEFORE de propósito: a ponte de conversões (AFTER UPDATE) precisa enxergar a
-- versão já incrementada no payload que envia.
create trigger opportunities_bump_stage_version
before update of current_stage_id on crm.opportunities
for each row execute function crm.bump_stage_version();

comment on function crm.bump_stage_version() is
  'Garante stage_version = anterior + 1 em qualquer troca de etapa, inclusive movimentos automaticos do parser.';

-- ---------------------------------------------------------------------------
-- Parte 2: ledger volta a descrever o repositório
-- ---------------------------------------------------------------------------

update supabase_migrations.schema_migrations
   set version = '20260923000004' where version = '20260918203014';

update supabase_migrations.schema_migrations
   set version = '20260924000000' where version = '20260918203606';

update supabase_migrations.schema_migrations
   set version = '20260925000000' where version = '20260919114524';

update supabase_migrations.schema_migrations
   set version = '20260925000001' where version = '20260919114551';

-- Registra a Parte 1, que está sendo aplicada aqui pelo editor e por isso não
-- entra sozinha no ledger.
insert into supabase_migrations.schema_migrations (version, name)
values ('20260925000002', 'crm_stage_version_guard')
on conflict (version) do nothing;

commit;
```

## Conferir depois de rodar

```sql
-- Deve listar as 10 migrations com os mesmos nomes dos arquivos do repo,
-- todas começando em 202609 22/23/24/25.
select version, name
  from supabase_migrations.schema_migrations
 where version >= '20260922'
 order by version;

-- Deve devolver uma linha: o trigger novo.
select tgname from pg_trigger
 where tgrelid = 'crm.opportunities'::regclass
   and not tgisinternal
 order by tgname;
```

O teste de verdade da Parte 1 é mover um card pelo painel duas vezes: a versão
tem que sair de N para N+1 e depois N+2. Antes, movimento automático do parser
não mexia no número.
